# KSSMA-Re 局域网怀旧复原评估与路线图

## 结论

项目可以继续研发，而且已经越过“只能启动客户端”的早期阶段。当前唯一客户端基线能在
Android 4.4.2/API19 ARM 环境完成启动、登录和主菜单；探索主路径、单次扭蛋和卡组编辑也已经
有部分客户端实机证据。现有 Node.js 服务端、JSON 存档、可复现 flow 和 native 路径卡足以支撑
继续做协议考古。

它还不是功能完整的私服。最主要的缺口不是普通 Web 开发，而是客户端原生代码所要求的请求、
响应、scene 和存档约束尚未全部恢复。后续必须继续按“一条流程边、一个变量、一个 artifact”
推进，不能用 HTTP 200 或一个看似正确的页面替代客户端验收。

本项目的目标边界保持为自备原始游戏文件、仅本机或可信局域网怀旧体验；不提供公网服务，也不
把客户端或原始游戏资产作为项目分发物。

## 当前能力边界

| 系统 | 当前状态 | 已有证据或限制 |
| --- | --- | --- |
| 启动、登录、主菜单 | 已验收 | 唯一 APK 基线；背景、角色、入口、BGM、语音和点击反馈已验收 |
| 探索主路径 | 初步完成 | 秘境、楼层、关卡、行走、AP、升级、普通完成和下一层已有 flow；守护者、战斗、妖精和深层奖励冻结 |
| 扭蛋 | 部分可玩 | 单抽、结果页、返回、付费重试、持卡与货币持久化已验收；非法请求的原生错误对话框路径未闭合 |
| 卡组 | 部分可用 | 进入、队长模式、内存编辑和保存请求捕获已验收；保存响应会意外回主菜单，持久化仍冻结 |
| 战斗 | 入口骨架 | 有 route/scene 样本，不足以证明选择对手、开战、回合推进或结果闭环 |
| 妖精 | 未闭环 | 发现、遭遇、参战、共享状态和结束迁移尚无完整流程证据 |
| 奖励结算 | 未闭环 | 掉落、经验、货币、卡牌、升级和幂等持久化尚未作为同一事务验收 |
| 管理后台 | M1 已完成 | 可查看系统/进度摘要，安全修改玩家基础字段；复杂进度和卡组保持只读 |
| 局域网用户 | 单活动存档 | 当前 `KSSMA_PLAYER_SAVE_PATH` 只指向一个活动玩家存档，不等于多账号并发服务 |

## 管理后台路线

M1 已提供 `/admin/`，使用与原作王城相近的视觉语言。它复用了现有存档读取和原子写入路径，
仅允许修改名称、阵营、等级/经验、AP/BC、金币、MC、友情点、扭蛋券和持卡上限。默认只有服务端
本机可写；设置 `KSSMA_ADMIN_TOKEN` 后，局域网写操作必须携带令牌。

下一阶段不应直接提供“任意 JSON 编辑器”。系统与玩家设置需要分三类开放：

1. 可即时安全修改：玩家展示信息、资源和已经闭合的货币/容量字段。
2. 需要完整一致性校验：持卡实例、队长、卡组槽位、探索位置和解锁状态；必须先闭合对应
   flow/native 契约，再提供事务式表单。
3. 需要重启或重载：世界信息、端口、回调地址、masterdata 映射和游戏内容基线；后台可以生成
   配置并明确显示“待重启”，但不能静默热改正在服务的进程。

建议的 M2 成功标准是：增加只读运行诊断、存档快照/恢复、变更审计，并为每次写入做跨字段校验；
暂不增加多用户 CRUD。只有先确定登录账号到独立存档的映射、并发写策略和客户端会话绑定，才进入
M3 多用户管理。

## 玩法恢复顺序

### 1. 先稳住共享玩家数据

扭蛋、卡组、探索结算和战斗都依赖同一组持卡、卡牌 master、卡组槽位、BC/AP 和货币数据。先把
现有 D5/D6 卡组保存阻塞和扭蛋非法请求的客户端错误路径收束，避免后续每个系统各写一套互相冲突
的数据模型。

成功标准：合法卡组能被客户端保存、重新进入后仍一致；非法卡组和余额不足不会写存档；现有扭蛋
和探索回归 flow 全部通过。

### 2. 深层探索只恢复下一条真实边

从已验收的普通楼层完成状态出发，选择第一个有静态证据支持的守护者或事件入口。新增一个复用
既有登录、server 和 artifact 收集能力的 flow scenario，同时记录：

```text
完成楼层后的用户动作 -> 请求/响应 -> scene/UI 迁移 -> 下一次点击目标或下一条 route
```

成功标准：请求参数、响应父节点、可见页面和后续点击目标至少形成一个闭环。此阶段不同时实现战斗
结果、妖精和奖励结算。

### 3. 战斗做最小纵切，不做通用战斗引擎

第一轮只恢复“已验收入口 -> 对手/队伍确认 -> 战斗场景出现”。第二轮再恢复一个可重复的确定性
回合，第三轮才接胜负结果。所有数值先来自已经恢复的卡牌 master 和玩家卡组，不新造第二套角色
属性来源。

成功标准：客户端进入真实 battle scene，至少一回合状态由请求/响应或已确认的本地逻辑推进，并且
失败不会污染存档。只有胜负 scene 闭合后才允许写战绩或奖励。

### 4. 妖精作为独立状态机

分开验证发现、列表、遭遇、参战和结束五条边。妖精共享/协作在单玩家局域网基线下可先使用明确的
本地简化，但必须以 `ponytail:` 标注上限和未来多用户升级路径。

成功标准：发现状态可持久化；进入/返回不重复错误 route；结束状态可以交给统一结算层。

### 5. 奖励结算最后接入统一事务

奖励不是单独画面问题。一次结算必须同时校验来源事件、掉落内容、容量、经验/升级、货币和重复请求。
先用确定性固定奖励闭合客户端画面，再增加随机池。

成功标准：同一结算请求重放不会重复发奖；结果页可见；返回后主菜单与存档一致；重新登录后仍一致。

## 每轮交付门槛

每轮控制在 90 分钟以内，并在开始前写清 Frontier、Success、Non-goal 和 Stop。服务端修改至少运行：

```powershell
conda run -n KSSMA-Re node .\server\test-bootstrap-server.js
```

玩法修改必须新增或复用 `flow -Scenario <name>`，交付 `summary.json`、`requests.jsonl`、
`events.jsonl`、关键截图和 logcat。Node 自检通过只能证明服务端没有破坏已有契约，不能替代客户端
玩法验收。

## 建议的下一回合

继续当前项目主线，优先处理卡组保存的当前模型响应/返回行为，或在其静态证据仍不足时完成只读
classifier；不要在同一回合并行改卡组 XML、探索守护者、战斗和后台数据表。后台的下一次改动则以
存档快照、恢复和变更审计为单独 M2 回合。
